# 识别契约与验收

## 已接入的第一阶段

新 MinerU 识别结果使用 `EVIDENCE_ONLY_V1`。字段证据在页面决策前留存；案件加载、平账与合并不能依据邻页或余额猜改这些流水的账号、日期、方向、金额和余额。人工核对仍可更新现行字段，原始证据保留。

页面上明确的唯一账号可用于身份决策。银行名称未知不影响账号有效性；同页多个账号不能折叠成一个；来源文件与页码共同定义页面。既有数据暂保留旧的数字纠错兼容逻辑，只有重新识别的数据进入新契约。

文档级身份决策集中在 `documentOwners.ts`：只接受原始内容确实包含的账户清单账号。同户名短账号仅在清单有唯一完整后缀匹配时关联，保留原账号和 `SUGGESTED` 决策；无匹配或多匹配均不处理。这里的关联仍是可复核的系统建议。银行名称冲突独立提示，不用银行缺失触发整套身份继承。

双路读取按完整候选选择，禁止按行数拼接或整体偏移年份。行数相同但字段不一致仍待核对。更多行的候选不等于真值。当前候选冲突会进入现有逐行核对界面。

## 离线重放

通过现有自动化接口运行测试，新版 `result.json` 的 `recognitionPages` 包含来源块（以及可用的坐标）、各路候选和页面决策。仅调试模式提供这份完整检查点集合。可运行：

```sh
npm run recognition:replay -- /absolute/path/result.json /absolute/path/ground-truth.json
```

重放不调用识别服务；按来源文件和运行编号隔离，只使用每份文件的最后一次运行。缺页直接失败，不拿旧运行补齐。当前重放覆盖页面决策之后的文档账号关联、合并、规范化；重新比较候选或修改模型提示词需另行重跑对应阶段。

## 标准答案

真实案件数据保存在已忽略的 `test-data/`，不可提交。识别输出不得自动标为人工真值。人工标注需提供：

```json
{
  "version": 1,
  "status": "SOURCE_CHECKED",
  "reviewedBy": "核对人",
  "documents": [{
    "documentId": "DOC_文件内容哈希",
    "completePages": [1],
    "rows": [{
      "page": 1,
      "row": 1,
      "fields": {"accountNumber": "90000001", "amount": 10, "direction": "IN"}
    }]
  }]
}
```

`completePages` 必须包括该页所有交易行；空白页填写该页但不填写行。`row` 是从 1 开始的本页交易物理顺序。只评估已标注字段；完整行准确率仅代表这些字段一致，不能用部分标注声称整行所有字段正确。模型串行或漏行引起定位偏移会计为错误。

可在每个文档增加 `accountNumbers` 作为该文档的完整账户清单（包括无交易账户），同时检查虚增与漏掉账户。本地 `test-data/recognition/06-account-ground-truth.json` 仅标注了此前原件核对确认的 5 个账号和 40 行账号归属；没有将本次大模型输出自动标为日期/金额/银行名称真值。

合成验收覆盖：未知银行但账号明确、同页多账号、跨文件相同页码、重复规范化与保存加载、双路数量相同内容冲突、页中漏行。真实样本应按银行/账单版式/来源文件划分开发集和保留集，不能将同一账单的相邻页拆到两边。余额平衡不是标准答案，也不是字段正确率。

## 后续阶段边界

尚未实现：服务端持久任务队列（关浏览器后继续）、经过真实标注集验收的通用账单分组、完整列映射及新的候选差异对照界面。第三阶段已接入初版分组提议与边界校验，详见下文，但不能把合成测试通过描述为长文件识别已全量验收。当前页面级模型仍直接输出流水，原 PDF 补识别仍使用既有接口。

## 第二阶段：有限跨页参考与本机续跑

逐页整理请求现在可附带 `context`：只匹配原文明确且完全相同的 12–32 位数字本方账号；同页多个本方账号、短号、未知账号或银行名称冲突时不传参考。最多提供两页的页眉和显式 HTML 表头，保留原页码、块号，不复制其他页面的交易。目标页内容优先，表头列数/顺序无法对应时仍留待核对。这是保守的同账号参考层，不等于已实现通用账单分类、无页眉续页归属或完整列映射；不会为每页再增加一个模型请求。

普通上传已接入 IndexedDB 检查点。原始 MinerU 文档只存一次，逐页候选分别保存；按用户、案件、文件内容身份、被调查人、识别版本隔离。页面请求及其参考内容的 SHA-256 变化时旧页结果不复用。读取/保存失败不丢弃本次结果，界面提示续跑可能不可用。`RECOGNITION_REVISION` 必须随提示词、模型配置、提取或决策策略变化一并升级。

“继续未完成页”复用已保存且数量完整、页面类型已知、无待核对字段的页面；不冻结失败或候选冲突页。“从头识别”忽略缓存并清理该文件旧进度；未识别到流水的文件默认从头识别，避免重复复用空结果。数据按来源重新合并，不把旧运行和新运行重复追加。文档删掉或案件删掉时同步清理当前用户对应检查点。缓存超过 7 天不再复用（不代表浏览器一定在第 7 天物理删除）。

这只支持**同一浏览器、同一用户、同一案件重新上传相同文件后的续跑**。关闭页面会停止执行；尚无跨设备恢复、服务端队列或自动恢复上传列表。首次 MinerU 请求还没返回前中断，仍需重新读取文档。

验证命令：`npm test`、`npm run build`、`npm run test:recognition-storage`。最后一项使用独立 Chrome 测试配置和合成数据验证真实 IndexedDB 的刷新恢复、输入失效、身份隔离和删除；其他系统可用 `CHROME_PATH` 指定 Chrome 可执行文件，不调用识别服务。

## 第三阶段：账单规划与续页建议

普通 PDF 上传的 PAGE 路径默认先调用 `/api/plan-statements`：模型仅输出页面类型、带原文引用的本方账号/银行/表头和 START/CONTINUE/UNKNOWN。采用结构化输出约束，并再次验证原文引用的页码、块号及逐字内容。原始提议保存在 `statement.descriptor.proposal`，校验后的描述与最终连续分组保存在逐页检查点的 `statement` 字段中；离线重放与后续诊断可见，不影响原始交易候选。

分组只用有上限的内容摘录；紧凑账户表尽量完整保留。每批最多 8 个目标页并附前一页作为跨批次参考，并发 2。这个数量只限制导航元数据请求，不切分或裁掉交易提取内容，也不限制账单长度。逐页流水仍接收原始完整有序内容块。成功且无疑点的分组批次可续跑；提示词/契约变更已升级识别版本。前后端请求都有时限；某批分组服务失败后，尚未开始且没有缓存的分组批次直接降级，避免长文件逐批等待超时。交易提取仍继续。

连续账单必须有两页原文引用；跨银行、换账号、新打印序列、账户列表、多账号、未知页、缺页或低可信关系会切断关联。原文明确账号/银行与模型描述冲突时也停止关联。同账号参考被限制在同一连续分组中，不再跨新打印序列寻找表头。

无账号续页只能获得 `PROPOSED_CONTINUATION` 参考，**不是已确认的本方账号**。模型仍不得复制参考页账号，后处理也不改写它。若提取结果仍无账号，核对提示明确给出参考页、建议账号和检查事项，仅关联未明确归属的流水；普通分组故障为参考提示，不冒充漏行或金额错误。账号为空的账户资料页不得视作完整账户清单。通过 `statementPlanning: false` 可在诊断时回退第二阶段路径；生产默认开启。

初版真实服务测试只区分了文书页、账户列表页和流水页，却返回空账号数组；这不等于完成账户归属。后续定位与修复见下文。仍未重跑完整交易提取或 128 页文件，不能把模型自报的高置信度当作验收。

### 表格账号证据修复（v4）

使用相同本地接口做对照：普通文字中的合成本方账号可以输出，而三页样本中 HTML 账户表的模型原始 `proposal.accounts` 就是空数组，不是校验阶段删掉。第 2 页完整账户表仅 2671 字符，没有被当前摘录预算截断。提示词原先要求一个连续引用同时覆盖栏名与账号，对表头和数据单元格相隔较远的表格不合适；开头“只规划页间关系”的任务描述也没有充分强调必须读取所有明确账号。

修订任务说明后，允许并要求分别引用：`accounts[].evidence` 指向账号所在原始单元格，`headers` 指向同表的原始表头。两者都必须是原文连续片段、页码一致、块号相同；缺少有效同表表头的表格账号不采纳。重复账号只按完全相同的数字（去空格/连字符）去重，不按尾号、余额或相似数字合并。原始提议中的重复与被拒绝字段仍保留。

真实服务复测使用此前保存的三页文字，而不是重新上传 PDF：第 2 页得到 5 个不同的完整账号，第 3 页得到 3 个不同的明细账号。第 2 页与现有人工标注清单比对一致；第 3 页短号按该清单唯一匹配后，与人工标注中的 3 个明细账户一致。此结果仅验证这份样本的规划元数据，不代表完整流水的金额、日期、余额或其他银行的识别准确率。新增合成测试覆盖远离表头的单元格引用、缺失/跨表表头拒绝、重复账号严格去重和原始提议保留。

### 三页样本的离线字段验收

此前保存的完整候选经当前离线归户、合并、规范化后，40 行、200 个已标注字段全部匹配，没有多出或漏掉账户。此验收只证明该保存候选在当前后处理下与上述视觉核读基准一致，不证明最新提示词重新上传后的输出，也不解除双路候选冲突或银行名称冲突的待核对状态。重新上传敏感银行文件的完整外部服务测试尚待明确授权，未执行。

### 实测后修复：定点核对与状态隔离（v5）

`candidateReview` 独立记录两路读取的字段差异、未匹配行或歧义行及其人工处理状态，不再通过整页降低置信度来承载冲突。只有账号和日期在两份候选中均唯一时才逐字段比较，比较包括日期时间、方向、金额、余额、对手方名称/账号与摘要；同日多笔、账号/日期缺失或改变时保守提示无法唯一对应，不按位置、金额或余额强行配对。仍选择一份完整候选，不拼接或补写财务字段。候选顺序或数量差异仍有独立页面完整性核对。

受保护流水不再经过零金额结息/减免规则自动清除疑点；读取失败的 0 元仍要求人工确认，明确读出的零金额不单因数值为零报错。行级人工确认可以接受真实的 0 元；只确认部分字段不会清除尚未处理的候选差异。原始候选、差异值与人工处理状态分别保留。

核对队列按来源文件身份和原件页码合并，弹窗包含该页所有账户的行级任务；保存时问题仍归各自账户，不跨文件传播。没有实际人工确认记录时，界面只显示系统检查状态；无流水账户显示“仅账户资料，未提供流水”。页面提示与逐行问题分开展示，具体差异直接显示在对应字段任务中。

银行名称仅采纳账单规划中有当前页有效原文引用的名称，或通过明确账户清单关联取得的此类名称；无依据的候选名称不进入正式账户，原始候选不修改。没有规划证据的诊断回退路径也保守显示“待核验银行”。银行名称缺少依据属于身份参考提示，不当作流水漏行。

新增 `npm run test:recognition-review` 使用独立浏览器和合成数据，禁止外部请求，实际验证定点填写、零金额确认、跨账户保存、其他文件隔离及状态标签。不能把这一界面测试描述为重新识别了真实 PDF。

最终验证：193 项单元测试、类型检查、生产构建及浏览器交互测试通过。浏览器还验证部分行已确认时整页记为无法确认不会覆盖已处理行，以及删除重复行不自动确认剩余问题。真实 PDF 未再次外发；以下回放保留的未读取金额仍是实际待办，不因为代码测试通过而解除。

已保存的三页实测可用 `npm run recognition:replay -- 结果.json 标准答案.json --reselect` 离线重新执行当前候选比较与后处理；不重新调用模型，也不重做分组提示词。此次回放保留 5 个账户、40 行，数字未改动，具体冲突为首行余额和尾部 7 行，共 8 行；另需清点原件行数。5 个金额虽然数值为 0，与视觉核读基准一致，但候选仍带金额未可靠读取标记，所以严格验收为 195/200 个可信字段，5 个 `UNREADABLE_VALUE`，不能再用旧规则清除疑点后宣称全量通过。尚未重新外发该 PDF，未验收其他银行或长文件。

### 完整文件实测后的文档级校验（v6）

128 页真实文件的首次测试完成导入，但发现账号数字误读导致同一账户分裂、重复版式交易重复计数、分组失败后银行名称丢失，以及结构完整的 OCR 表仍含错误数字。这不是准确性验收通过。以下策略取代上文 v5 的相应限制：

- 分组截断只影响当前批；对输出不完整的批次最多缩小范围重试一次，成功的子批保留。连续可用性错误才停止后续服务请求。接口区分输出上限、服务不可用和超时，客户端保留取消与超时边界。
- 银行身份不仅能来自规划引用，也能来自本页独立银行抬头或文档内同一精确账号的有据关联。不从文件名、卡号前缀、对手方银行或相邻页猜银行。真实补测发现直接 PDF 模型也会猜银行，因此其无可定位原文依据的名称仍只保存在候选中，不进入正式账户；也不再仅为补银行名称重读整页流水。
- OCR 页面账号不再覆盖另一路已明确读取的账号；冲突保留为本方账号字段任务。资料页即便分类为 DOCUMENT，其带引用的明确账户资料也可参与归户。
- 司法查询回执等资料页中的独立“账号”“对应卡号”标签可直接建立有来源的账号/卡号关系，不依赖规划器是否返回账号数组；仅完整且唯一的明确关系参与，排除对方账号标签。完整文字候选不会仅因为原 PDF 候选行数更多就被替换，避免新增幻觉行影响账户合并与计数。
- 相差一位数字不是合并依据。只有目标账号出现在有据账户资料中、原账号未被独立列出、同源同户名、至少三个非零金额交易在至少两天的日期/方向/金额/余额一致、覆盖待关联组至少 80%、且目标唯一，才提出临时归户。保留原始账号与 SUGGESTED 决策，人工可更正，不改金额。已人工确认的账号不被此规则覆盖。
